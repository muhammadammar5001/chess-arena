# Architecture

## Overview

Chess Arena is a vanilla-JavaScript single-page app served by a small Node.js backend. The browser owns rendering, local game state, AI, and the coin/profile economy. The server owns online rooms, move validation for multiplayer, and optional MongoDB-backed leaderboard profiles.

```
Browser
  index.html + CSS
  app.js ── chess-engine.js / ai-engine.js / pieces.js
         ├─ multiplayer.js ── WebSocket ── server.js
         ├─ platform.js ── PlayGama Bridge (identity only)
         ├─ storage-service.js ── YouTube cloud / Bridge / localStorage
         └─ ad-service.js ── host ad adapter or mock

server.js
  Express static hosting
  POST /api/leaderboard/sync
  GET  /api/leaderboard
  WebSocket rooms / matchmaking / timers / chat / abilities
  models/User.js ── optional MongoDB
```

## Client

`public/js/app.js` is the central controller. It manages screen navigation, modals, the board, timers, audio, chat, the shop, profile hydration, match-stat updates, and leaderboard rendering. It is intentionally monolithic for now; the engine, transport, platform, and persistence modules are separated.

### Screens

Home, AI difficulty, room, matchmaking, waiting, game, profile, shop, abilities, leaderboard, how-to, and victory recap. Every screen is a `.screen` element in `index.html`; `App.showScreen()` toggles the `active` class.

### Board and rules

`ChessEngine` implements legal moves, check/checkmate, castling, en passant, promotion, draws, and Tactical Mode abilities. Freeze and Divine Shield expire from `completedTurns`, not from total move/ability events, so instant abilities and Second Chance do not consume their duration. Undo restores the snapshot taken before the move, including those status counters. `AIEngine` uses minimax with alpha-beta pruning and a time budget based on difficulty. Pieces are inline SVG generated by `pieces.js`.

### Local state

| Key | Purpose |
| --- | --- |
| `player_profile` | Cloud/local profile document. On YouTube Playables this key lives in `YT.getCloudStorage()`. |
| `chessarena_player_profile_mirror_v1` | Immediate local mirror of the latest profile. Used if cloud reads fail. |
| `chessarena_player_id` | Mirrors the profile's `usr_<16 hex>` ID for legacy code paths. |
| `chessarena_coins` | Soft coin balance mirror. |
| `chessarena_abilities` | Two equipped abilities. |
| `chessarena_board_theme` | Equipped board cosmetic mirror. |
| `chessarena_stats_v1_<identity>` | Legacy rating and AI/online W/L/D. Read only for local-mode migration/fallback. |
| `chessarena_platform_profile_v1` | Cached PlayGama identity (the `mock` adapter is ignored). |

## Profile persistence

`public/js/storage-service.js` exposes a single `window.ChessArenaStorage` manager with `init()`, `loadProfile()`, `saveProfile(profile)`, `updateMatchStats(result, ratingDelta, options)`, and normalization helpers. All public APIs are async.

### Backend priority

1. YouTube Playables native `YT.getCloudStorage()` when the SDK supplies `getItem`/`setItem`.
2. PlayGama Bridge storage when a real platform ID is present. The Bridge `mock` platform returns no identity and is skipped.
3. `localStorage` for localhost and standalone builds.

The YouTube SDK can initialize asynchronously. On a YouTube host the manager waits up to five seconds for it; local/standalone startup is never delayed.

### Schema and sanitization

```json
{
  "playerId": "usr_<16 hex>",
  "username": "PlayerName",
  "rating": 1200,
  "rank": null,
  "stats": {
    "wins": 0,
    "losses": 0,
    "draws": 0,
    "totalMatches": 0,
    "winStreak": 0,
    "bestStreak": 0
  },
  "coins": 1000,
  "equipped": { "board": "classic-oak" },
  "matchHistory": [],
  "lastUpdated": 0
}
```

Every loaded or incoming object is passed through `normalizeProfile()`:

- Usernames are reduced to 3–16 alphanumeric characters.
- `playerId` must match the generated `usr_` shape; unsafe or legacy IDs are replaced.
- Rating is clamped to 100–4000, coins to 0–1,000,000,000, and stat counters to 10,000,000.
- Board IDs are restricted to the shipped cosmetic set.
- Optional `matchHistory` keeps at most the last 30 sanitized entries.

### Writes and failure handling

Every save writes the local mirror immediately, then coalesces cloud writes so they are at least one second apart. The first write is immediate. If the cloud write fails (quota, network, missing SDK), the in-memory profile and mirror remain current and the manager retries with exponential backoff, up to five attempts. Gameplay never waits for the cloud; `updateMatchStats()` resolves after the mirror/current profile is safe.

A cloud-backed account whose cloud record is empty is treated as a new player. The local mirror and legacy keys are not migrated into it because they may belong to another account. The mirror and legacy keys are used for local play or when a cloud read fails.

### Onboarding

`initializeProfilePersistence()` loads the profile after local UI initialization. If the loaded profile has no valid username, the **Enter Player Name** modal appears. The name is sanitized as the player types and must be 3–16 alphanumeric characters. Existing valid profiles skip the modal and hydrate the name, rating, coins, equipped board, and cached rank immediately.

Online actions are gated by `ensureProfileReady()` and a pre-match leaderboard sync. This avoids starting a rated game with a profile the server has never seen.

## Match stat flow

### AI games

The local profile is updated with an Elo estimate against the difficulty's opponent rating (easy 800, medium 1200, hard 1600). The profile is then persisted through the storage manager and synced to the server leaderboard.

### Online games

1. The client syncs its cloud totals with `POST /api/leaderboard/sync` before matchmaking/room join when the last sync is stale.
2. The server updates both players' MongoDB rows in `finishGame()` using Elo K=32 and increments wins/losses/draws, total matches, win streak, and best streak.
3. The server sends `stats_update` with `gameId` and authoritative totals to both players.
4. `applyServerStats()` accepts the server totals only when they are not older than the cloud profile's total, writes them to the canonical profile, and schedules another leaderboard sync.
5. `recordGameResult()` records the match exactly once per `gameId`, appends the sanitized match-history entry, and refreshes rank/leaderboard. `gameId` matching plus a profile revision guard prevent stale async writes from double-counting or overwriting a newer authoritative result.
6. The sync response also carries canonical server stats. On startup/reconnect, the client adopts them when the server total is equal to or higher than the cloud total, so a match finished after the tab closed still appears locally.
7. If MongoDB is unavailable, the client keeps its cloud/local Elo estimate and retries the leaderboard sync in the background. `online` events also trigger a retry.

## Server

`server.js` exposes static files, JSON leaderboard endpoints, and a WebSocket endpoint on the same port.

### HTTP endpoints

`POST /api/leaderboard/sync`

```json
{
  "playerId": "usr_<16 hex>",
  "username": "PlayerName",
  "rating": 1224,
  "stats": {
    "wins": 2,
    "losses": 0,
    "draws": 0,
    "totalMatches": 2,
    "winStreak": 2,
    "bestStreak": 2
  }
}
```

The route sanitizes and clamps the payload, upserts the MongoDB profile, resolves name collisions with a numeric suffix, and returns:

```json
{
  "success": true,
  "username": "PlayerName",
  "rating": 1224,
  "stats": {
    "wins": 2,
    "losses": 0,
    "draws": 0,
    "totalMatches": 2,
    "winStreak": 2,
    "bestStreak": 2
  },
  "currentRank": 2,
  "totalPlayers": 7,
  "topPlayers": []
}
```

A strictly larger client total advances the server profile (offline/AI progress). If the incoming total is equal or lower, the server keeps its existing Elo/streak and returns those values; the client adopts them. This prevents a reconnect with an older cloud snapshot from erasing a PvP result the server already recorded. Usernames can still be renamed on an equal total.

`GET /api/leaderboard` returns the top 100 registered profiles with `rank`, `rating`/`elo`, wins, losses, draws, streaks, and `totalPlayers`. Rows are sorted by Elo, then wins, then username. If Mongo is not connected, the same shape is served from an in-process memory table with the same merge rules.

### WebSocket flow

1. Client connects and sends `authenticate` with the profile's `playerId` and, when available, display name.
2. Server looks up the profile and auto-creates a fallback row if needed. It replies `auth_success`; `auth_offline` means MongoDB is unavailable and stats stay local.
3. Room creation: `create_room` → `room_created`; the host waits on `screen-waiting`.
4. Joining: `check_room` → `check_room_result`; `join_room` → `game_start` to both colors.
5. Matchmaking: `find_match` → `waiting_for_match`; when paired, both receive `game_start`.
6. Moves are validated by the server engine and relayed as `opponent_move`, with `timer_sync` updates. The server owns the clock, includes the effective timers in `game_start`, and broadcasts `timer_sync` every second so background-tab throttling, host pauses, and reconnect delays cannot desynchronize the two clients.
7. Game end broadcasts `game_over`; the server updates Mongo profiles and sends `stats_update` when possible.
8. Rematch, draw offers, chat, spectating, and abilities use dedicated message types.

Rooms are in-memory and expire through the existing heartbeat/cleanup logic.

### Data

`models/User.js` stores `playerId`, `username`, `elo`, wins, losses, draws, `totalMatches`, `winStreak`, `bestStreak`, `lastUpdated`, and `createdAt`. MongoDB is optional. `GET /api/leaderboard` returns the top 100 registered players, including legacy rows. Usernames are 3–16 alphanumeric characters; duplicate names are suffixed (for example `CloudAce2`) and the client adopts the returned canonical name.

On startup, `migrateUserIndexes()` drops the pre-rebrand `walletAddress_1` unique index and ensures sparse unique indexes on `playerId` and `username`. Legacy profiles that predate `playerId` remain visible but cannot authenticate; no destructive cleanup is performed.

## Platform adapter

`platform.js` loads the PlayGama Bridge, waits briefly for authorization, and caches name/avatar/platform metadata. It never blocks gameplay and ignores the Bridge `mock` adapter. YouTube Playables does not provide player authorization, so identity comes from the cloud profile/name modal, not a platform account. Profile persistence is handled separately by `storage-service.js`.

## Coins

Coins are a soft, non-purchasable currency. The starting balance is 1,000. Hints and undo cost coins; there is no purchase, withdrawal, or transfer path. Coin changes are persisted through the profile store and mirrored locally.

## Playables deployment checklist

- Validate `YT.getCloudStorage()` availability and behavior inside the actual Playables runtime. It cannot be exercised on localhost; localhost uses `localStorage`.
- Replace the external PlayGama Bridge CDN with the approved Playables integration/build step if the final distribution requires it.
- Replace `ad-service.js` mock adapter with the host ad adapter.
- Provide a hosted WebSocket backend for multiplayer; AI and local profile saves work without a backend.
- Validate portrait orientation and story requirements against the current Playables checklist.
- Check the final bundle against the Playables size limit (large PNGs under `public/assets` are the main weight).
- Keep the PlayGama `mock` platform ignored for identity and cloud data.

## Tests

`npm test` runs 14 characterization tests covering board setup, pawn/knight movement, castling, en passant, checkmate, Freeze, Swap, Second Chance, Divine Shield, Pegasus Jump, and the turn-based Freeze/Shield interactions with instant abilities and undo, plus 12 economy tests. Browser-level verification additionally covers onboarding, profile hydration, AI and PvP stat updates, leaderboard rank rendering, cloud-adapter simulation, and sync retry behavior.
